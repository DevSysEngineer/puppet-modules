# Lint Development Instructions

## Scope And Reading Route

Read the [repository instructions](../../AGENTS.md), [tooling instructions](../AGENTS.md), and [lint README](README.md). This file governs development of lint checks, registration, profiles, detection, autofix and lint documentation. For every linter change, follow the applicable development and validation procedures here and review the result against them. The README owns public usage, architecture, the check registry and test commands; the three rule documents remain the Puppet norm owners throughout the repository.

For each affected check, follow its registry link to the authoritative rule. In particular, preserve the existing review routes for [configuration ownership](docs/CODE_RULES.md#instellingen-bij-hun-eigenaar-houden), [external-command package dependencies](docs/CODE_RULES.md#packageafhankelijkheden-bij-externe-commandos), [runtime source selection](docs/OPERATIONAL_RULES.md#actuele-hosttoestand-uit-kernelgegevens-bepalen), [shell helper boundaries](docs/OPERATIONAL_RULES.md#shellhelpers-op-een-herkenbare-taak-afbakenen), [Puppet input in shell templates](docs/OPERATIONAL_RULES.md#puppet-waarden-rechtstreeks-in-shelltemplates-invoegen), and [inspection status](docs/OPERATIONAL_RULES.md#vastgestelde-afwijkingen-en-onvolledige-inspecties-onderscheiden) when those responsibilities are affected.

## Check Development

- Start from the existing code norm and distinguish automatic evidence from manual review. Check whether a native check, installed plugin or projectcheck already handles the contract; extend it where possible instead of adding competing detection or correction.
- Review every new or changed lint rule for safe automatic correction per diagnostic variant, including existing checks without autofix. Implement a fix when available information uniquely determines the correction and preservation of behavior and data can be demonstrated. Implement a safe subset when only part is unambiguous. Never implement a fix that relies on unproven assumptions or design choices that could change behavior or damage data. Record the assessment under the rule's `Autofix` and `Autofixvoorwaarden`; for absent or partial fixes identify the missing information, manual decision or technical limitation.
- Follow the [check registration and native architecture](README.md#technische-werking-van-de-checks). Keep each manifestcheck in its own file under `lib/project_lint/checks/`, named after the check without `project_`, with its `ProjectLint::Checks` module, `PuppetLint.new_check(:project_...) { include CheckModule }`, `check` and optional `fix(problem)`. Add its ordinary `require` to `lib/project_lint.rb`.
- Diagnostics must identify the cause and a useful source position without arbitrary source values in diagnostics or JSON. Use `[review]` when analysis cannot establish the desired property or correction.
- Update the authoritative rule and [check registry](README.md#beschikbare-projectchecks) together, recording actual detection, autofix and manual coverage. Apply the root obligation for changes to general Puppet conventions.
- Test valid and invalid use, boundary cases and analysis limits through the real library entrypoint and native configuration. For packaging, configuration or CLI changes, also test installation, exit codes, loaded rules and isolation from personal options in an independent project. Use the [lint test commands](README.md#tests-uitvoeren-en-uitbreiden) during development and the root required checks before completion.

## Architecture Review

- Prefer Puppet-lint's native registration, configuration, diagnostics, suppressions and autofix APIs over custom infrastructure. Keep simple tokenchecks free of unnecessary AST analysis; preserve the shared analysis and loading contracts described in the [architecture](README.md#technische-werking-van-de-checks).
- Keep Ruby helpers in `ProjectLint` with conventional namespace-based require paths. Do not introduce top-level helper constants or mutable configuration captured at load time.
- Share helpers for concrete concepts such as resource attributes, comment boundaries, variable dependencies and modulepaths. Keep substantial independent analyses, such as backend origin or shell escaping, separate from their checks. Keep simple check-specific methods with the check. A larger analysis may be divided within the same file, for example into comment formatting, line width and suppressions, while retaining cohesion and the existing RuboCop rules. Extract only existing shared complexity or a substantial independent analysis; do not add speculative abstractions.
- Treat check names, severities, safe fix results, `PROJECT_TOOLS_MODULEPATH`, the entrypoint, shared configuration paths and reporting commands as public interfaces. Assess changes under the root release policy and validate the built package from an independent project. Keep consumer installation and CI examples aligned with the [supported structure](README.md#aanbevolen-projectstructuur), documenting deviations without duplicating implementations or shared profiles. Follow the [gem release procedure](README.md#een-gem-bouwen-en-versie-uitbrengen) and describe changes affecting consumers.

## Safe Autofix Development

- Inspect the actual bundle with `bundle exec puppet-lint --no-config --config .puppet-lint.rc --version` and `bundle show puppet-lint`. Reuse existing native, plugin and project detection and safe fixes. Use only the native Puppet-lint fix mechanism; do not add a formatter or autofix engine.
- Require every custom fix to be idempotent and to meet the [daily correction safety contract](README.md#werkwijze-bij-een-wijziging): safe, deterministic, scoped, preserving behavior, relationships, dependencies and configuration. Review the entire changed construct, preserve comments, validate generated Puppet syntax and verify that the resolved diagnostic disappears.
- Implement `fix(problem)` beside `check` in the registered check module. Preserve token objects and correction conditions during `check`; diagnostics refer to that context by index rather than exposing source values in JSON. Check every precondition before mutating tokens; use `PuppetLint::NoFix` when they do not hold so the original diagnostic remains.
- Use native `add_token`, `remove_token` and existing token properties. Reuse tokens other checks can alter, and calculate spacing from current token content. Line and column numbers still refer to the original source. Use [TokenHelpers](lib/project_lint/token_helpers.rb) for regions and whitespace, not a complete file parser or rewriter.
- Account for earlier fixes changing or deleting tokens after detection. Preserve the [fix interaction contracts](README.md#autofixinteracties), native `lint:ignore` and `fix(problem)` handling. A multiline correction must also check whether it would modify an ignored region.
- Add regression coverage for detection without mutation, exact output, clean rescanning and an unchanged second fix run. Include unsuitable input, suppressions, comments, strings, multiple problems, nesting and interactions with active upstream checks. Test native CLI writes and exit codes on temporary files, including configuration selection, partial corrections and unsafe cases. Support autofix only after the normal `--fix` invocation demonstrably writes the intended change and rescanning clears the diagnostic. Parser validation of fix output belongs to this contract; the root test scope excludes general module syntax suites.
- Keep normal CLI and CI runs check-only. Enable `fix` only in an explicit correction step and do not introduce a second formatter or automatic commit step.

## Test Maintenance

- Use the [existing test support](README.md#tests-uitvoeren-en-uitbreiden): ordinary `Minitest::Test`, the native lint helper and public configuration. Keep short input in Ruby, and use a fixture only when a larger or reused scenario becomes clearer. Retain explicit fixture selection and failure on empty fixture sets; do not introduce specialized base classes or fixtures inferred from method names.
- Use `assert_fix(before, after, :project_check_name)` for detection, exact correction, parser validation, clean rescanning and idempotence. Test unsafe constructs with `fix: true` and assert unchanged input. Preserve cross-check interaction coverage.
- Investigate a failure from its reported input and assertion. Run the affected test separately while developing and finish with the complete tool suite. When checking the GitHub output form with `GITHUB_ACTION=synthetic_test`, require the same diagnostic counts as ordinary output.

## Lint Documentation Boundaries

- Keep lint norms and public lint usage procedures in exactly four central Dutch documents: `README.md` for tooling usage, the daily lint workflow and the check registry, `docs/CODE_RULES.md` for general Puppet rules, `docs/DOCUMENTATION_RULES.md` for Puppet code comments, Puppet Strings, and interface documentation, and `docs/OPERATIONAL_RULES.md` for additional operational rules, following [language and authority](../../AGENTS.md#language-and-authority).
- Do not create separate documents per check, rule, small rule group, autofix, consumer, CI platform, or test topic. Any additional central lint document requires a separate, explicit architecture change; file size alone never authorizes an automatic fifth document. This local `AGENTS.md` owns development instructions, not a fifth collection of Puppet norms or a second check registry.
- Keep the general rules under `CODE_RULES.md`; do not introduce `STYLE_RULES.md`, since these rules also cover interfaces, parameters, dependencies, and resources. Do not use `REFERENCE.md` for lint rules; module `REFERENCE.md` files retain their Puppet Strings/API-reference purpose.
- Keep each of the four central lint documents strictly below 300 KiB (307200 bytes), guarded by a lint documentation contract test. On an overshoot, first review placement within the four assigned responsibilities. Never delete or shorten necessary content, combine independent rules to save space, or split automatically to meet the limit; any necessary fifth document requires a separate, explicitly reviewed architecture change.
- Preserve requirements, exceptions, warnings, detection limits, autofix conditions, supported usage routes, and manual review criteria during reorganization. Consolidating duplicate explanations must preserve every distinct condition and obligation.
- Keep the lint README's contents task-oriented around lint usage and tooling. Link clearly from the lint README to all three rule documents and between relevant sections in all four documents, following the [Markdown navigation requirements](../../AGENTS.md#markdown). Make the cumulative applicability of the three rule documents explicit in the reading guide.
- Keep both the repository quick start and the consumer quick start before the detailed lint reference in `README.md`, linking shared setup to `../README.md`. Keep the sole central check registry and maintainer explanations there, and link directly to the authoritative rule in `CODE_RULES.md`, `DOCUMENTATION_RULES.md`, or `OPERATIONAL_RULES.md` without duplicating full rules or the registry.
- General README brevity, selective-detail, and presentation guidance must not remove information or required fields from the lint guide. Apply the lint guide's documentation contract to its rule reference.

## Lint Documentation Maintenance

- Apply the lint README's [maintainer documentation contract](README.md#documentatiecontract-voor-maintainers) when changing rules, checks, diagnostics, profiles, configuration, procedures, or consumer interfaces.
- Review ownership using [authority and rule placement](../../AGENTS.md#authority-and-rule-placement), preserve meaning using [consolidation and placement](../../AGENTS.md#consolidation-and-placement), and record the previous location, preserved meaning, new location, and reason for each substantive move in the change review. Do not create another repository document for the migration record.
- Verify incoming links, anchors, inventories, and execution contracts with the documentation tests; review explanatory accuracy and preservation of meaning manually. Verify that each rule and its subordinate headings have one authoritative destination.
- Keep unresolved policy conflicts and unexecuted required checks visible according to [isolation and evidence](../../AGENTS.md#isolation-and-evidence). Do not describe the task as complete while required evidence is missing.

### Documentation Changes And Verification

- Apply the README's [documentation schema](README.md#documentatiecontract-voor-maintainers) when maintaining rule explanations, registry rows or usage procedures. Keep every independent Puppet rule at its one authoritative heading, all required fields in their exact order and the registry's exact columns. Do not omit, rename or combine required fields unless the owner explicitly requests a schema change; do not add a second rule numbering system.
- Verify each registered projectcheck has exactly one registry row; check missing, unknown and duplicate names separately. Verify runtime registration, both profile activations, diagnostic coverage and authoritative rule links as separate properties. Classify autofix per diagnostic variant, never merely by the presence of a fix method.
- When checks, diagnostics, severity, defaults, autofixes, suppressions, configuration, dependencies, reporters or consumer interfaces change, update the affected rule fields, README registry rows and procedures, implementation and tooltests together. Justify a conclusion of no documentation impact with the interfaces actually reviewed. Verify version claims against declared constraints and resolved dependencies; distinguish declared compatibility, installed versions, tested combinations and development policy.
- Verify changed configuration instructions against the installed CLI, loader and tests. Determine precedence per option type rather than assuming every later value wins. Test changed downstream procedures in an independent consumer project with its own Gemfile, lockfile, configuration and manifest selection. Validate each described installation route separately, including built packages when distributed; path installation does not prove Git or package installation. Check successful and failed commands, numeric exit status and report production; successful conversion must never hide failed lint or validation.
- Check correct and incorrect examples, each exception and boundary category, exact fixes, rescanning and an unchanged second fix run. Complete examples must pass the full named profile; manual norms must identify concrete review steps and criteria. Preserve the README's example labels and procedure context fields, defining variables and replaceable paths before use and starting a new context block when context changes.
- Preserve heading anchors without duplicate IDs and update incoming links when an owner moves. Record relocated, consolidated and corrected obligations, exceptions, warnings and usage routes with old and new locations and evidence in the change review. Automated tests verify inventories, links and execution contracts; manually review preservation and clarity. Do not change lint behavior or a norm merely to remove a documentation discrepancy; keep the norm and observed behavior distinct until the intended resolution is established.
